# 거래 신청부터 완료까지

## 무엇이 달라졌나

기존에는 판매자가 게시글의 SALE / RESERVED / SOLD를 직접 바꿨다. 그래서 누구와 예약했는지, 누가 구매했는지는 남지 않았다.

이제 `TradeRequest`가 게시글, 구매자, 판매자를 연결한다. 게시글 상태는 거래 진행 결과로 바뀐다. 원래 게시글 등록·검색·이미지 업로드·회원 로그인 구조는 유지한다.

```text
구매자: 게시글 상세 -> 거래 신청 POST
  -> 로그인 검사 -> 거래 폼 CSRF 검사
  -> TradeController -> TradeService.apply()
  -> 게시글 행 잠금 -> 본인 글/중복/판매 상태 검사 -> 신청 INSERT
  -> redirect:/trades -> GET으로 내 거래 목록 조회

판매자: 게시글 상세 -> 신청 목록 GET -> 예약 확정 POST
  -> TradeService.reserve()
  -> 작성자 검사 -> 신청 RESERVED + 게시글 RESERVED -> 함께 COMMIT

판매자: 거래 완료 POST
  -> 신청 COMPLETED + 게시글 SOLD + 나머지 대기 신청 REJECTED
  -> 함께 COMMIT -> 구매자와 판매자의 내 거래 화면에 완료 기록
```

## 상태와 정책

| 동작 | 누가 할 수 있나 | 신청 상태 변화 | 게시글 상태 |
|---|---|---|---|
| 신청 | 작성자가 아닌 로그인 회원 | 새 REQUESTED | SALE 유지 |
| 예약 확정 | 판매자 | REQUESTED -> RESERVED | SALE -> RESERVED |
| 대기 신청 취소 | 신청한 구매자 | REQUESTED -> CANCELLED | 유지 |
| 예약 취소 | 해당 구매자 또는 판매자 | RESERVED -> CANCELLED | RESERVED -> SALE |
| 거절 | 판매자 | REQUESTED -> REJECTED | 유지 |
| 완료 | 판매자 | RESERVED -> COMPLETED | RESERVED -> SOLD |

예약 중에도 기존의 다른 대기 신청은 남긴다. 예약을 취소했을 때 그중 다른 사람을 선택할 수 있기 때문이다. 완료할 때 남은 대기 신청을 모두 거절한다. 취소·거절 후에는 판매 중인 글에 다시 신청할 수 있다. 완료·취소·거절 상태를 다시 예약 상태로 되돌릴 수는 없다.

신청만으로 예약되는 것은 아니다. 여러 사람이 신청할 수 있지만 확정된 예약은 한 명뿐이다. 현재 버전은 판매자의 완료 처리를 거래 완료로 인정하며, 결제나 구매자의 수령 확인을 의미하지 않는다.

## 새 코드의 역할

| 파일 | 역할과 이유 |
|---|---|
| `trade/domain/TradeRequest.java` | 거래 신청 엔티티. 세 개의 지연 로딩 연관관계와 상태 변경 메서드를 가진다. |
| `trade/domain/RequestStatus.java` | 신청 상태를 문자열 상수 대신 enum으로 제한한다. |
| `trade/repository/TradeRequestRepository.java` | 신청 중복 확인, 신청 목록, 참여자의 거래 내역을 조회한다. |
| `trade/service/TradeService.java` | 권한·상태 규칙을 검사하고 하나의 트랜잭션 안에서 여러 엔티티를 변경한다. |
| `trade/service/PostTradePolicy.java` | 기존 게시글 수정·삭제·수동 상태 변경이 거래 규칙을 우회하지 못하게 한다. |
| `trade/service/TradeRequestView.java` | 화면에 필요한 값만 담은 DTO. 트랜잭션 안에서 엔티티를 읽어 만든다. |
| `trade/service/TradeConflictException.java` | 이미 예약되었거나 잘못된 상태 전환처럼 업무 규칙 충돌을 표현한다. |
| `web/trade/TradeController.java` | URL과 서비스를 연결하고 세션에서 로그인 회원 ID를 받는다. |
| `web/trade/TradeCsrf.java` | 세션에 임의 토큰을 만들고 거래 변경 POST의 토큰을 비교한다. |
| `templates/trades/list.html` | 내 거래/판매자의 신청 목록과 가능한 동작 버튼을 보여준다. |
| `db/migration/V7__create_trade_request.sql` | 기존 V1~V6는 변경하지 않고 거래 테이블과 FK·인덱스를 추가한다. |

`TradeRequest`에는 신청 당시의 제목과 가격도 저장한다. 취소 후 판매자가 글을 고쳐도 과거 신청 금액이 바뀌면 안 되기 때문이다. 구매자·판매자 이름은 현재 회원 정보에서 조회하며, 이름 변경 이력까지 저장하는 구조는 아니다.

## 트랜잭션과 동시성

`@Transactional`은 예약 확정에서 신청 상태와 게시글 상태가 함께 반영되도록 한다. 둘 중 하나만 저장되고 끝나는 것을 막는다. 예외가 밖으로 전달되면 DB 변경은 롤백된다.

하지만 트랜잭션만으로 두 요청의 동시 예약까지 해결되는 것은 아니다. `findByIdForUpdate()`는 `PESSIMISTIC_WRITE`로 게시글 행을 잠근다. 같은 게시글에 대한 신청·예약·취소·완료·수정·삭제는 모두 이 잠금부터 얻는다.

```text
요청 A: 게시글 잠금 획득 -> SALE 확인 -> 예약 변경 -> COMMIT, 잠금 해제
요청 B: 잠금 대기       -> 잠금 획득 -> RESERVED 확인 -> 409 충돌
```

신청 ID로 접근할 때는 먼저 게시글 ID만 조회하고, 게시글을 잠근 다음 신청 엔티티를 읽는다. 잠금을 기다리기 전에 낡은 엔티티를 영속성 컨텍스트에 넣지 않기 위해서다. 모든 변경에서 잠금 순서를 통일한다.

이 보장은 애플리케이션의 서비스 경로를 따르는 작업을 대상으로 한다. 운영자가 SQL로 직접 상태를 바꾸거나 새 코드에서 이 규칙을 우회하면 보장이 깨질 수 있다. 실제 운영 DB로 바꿀 때는 동일한 동시성 테스트를 그 DB에서도 실행해야 한다.

## 기존 코드 변경

- `TradePostRepository`와 JPA/JDBC 구현체에 잠금 조회를 추가했다. 기본 구현은 기존처럼 `@Primary`가 붙은 JPA다.
- `TradePostService`의 수정·삭제·수동 상태 변경에 잠금과 `PostTradePolicy` 검사를 추가했다.
- 대기/예약 신청이 있거나 거래가 완료된 글은 수정할 수 없다. 모든 신청이 취소/거절된 판매 중 글은 다시 수정할 수 있다.
- 신청 이력이 하나라도 있는 글은 삭제할 수 없다. 거래 내역이 게시글 FK를 사용하기 때문이다. 향후 숨김/보관 기능을 별도로 설계할 수 있다.
- 과거의 수동 상태 변경 URL로 RESERVED/SOLD를 설정할 수 없다. 거래 이력이 없는 과거 글만 SALE로 복구하는 호환 동작은 남겨 뒀다.
- 상세 화면의 수동 상태 버튼을 거래 신청과 신청 목록 링크로 교체했다. 상단에 내 거래 링크를 추가했다.
- 오류 처리기에 409 화면을 추가했다. 로그인 필요는 기존 로그인 이동, 타인 권한은 403, 없는 대상은 404로 처리한다.
- 기존 로컬 이미지 업로드 코드와 V6도 함께 보존한다. 새 거래 기능이 이미지 없는 예전 코드로 되돌리지 않도록 했다.

## 화면, 권한, 보안

버튼을 숨기는 것만으로 권한 검사가 되는 것은 아니다. URL을 직접 호출할 수도 있으므로 서비스에서도 판매자/구매자를 확인한다. 회원 ID는 폼 값이 아닌 로그인 세션에서 가져온다.

`TradeCsrf`는 로그인 사용자의 세션에 토큰을 보관하고 HTML hidden input으로 같은 토큰을 전달한다. 인터셉터는 POST의 토큰이 없거나 다르면 403으로 차단한다. 이 보호 범위는 이번에 추가한 거래 변경 URL이며, 앱 전체에 Spring Security를 적용한 것은 아니다.

목록 조회는 `@EntityGraph`로 필요한 게시글·구매자·판매자를 함께 로딩하고, 서비스 안에서 DTO로 변환한다. `open-in-view=false`여도 템플릿에서 지연 로딩 예외가 발생하지 않게 한다. 페이지당 10건이며, 거래 내역은 해당 구매자/판매자에게만 공개한다.

## 확인 순서

1. 두 계정을 만들고 일반 창/시크릿 창에서 각각 로그인한다.
2. 판매자가 글을 등록하고 구매자가 상세 화면에서 거래 신청한다.
3. 판매자가 신청 목록에서 예약을 확정한다. 상세 상태가 예약 중인지 본다.
4. 예약 취소 후 판매 중으로 돌아가는지 확인하고 다시 신청/확정한다.
5. 판매자가 완료한다. 양쪽 내 거래 화면에 완료 기록이 있는지 본다.
6. 다른 회원의 예약/완료 요청, 본인 글 신청, 두 번 누르기, 완료 후 수정/삭제가 차단되는지 확인한다.

`TradeFlowTest`는 실제 Flyway/H2/JPA를 사용해 이 흐름과 경쟁 요청을 검증한다. 기존 컨트롤러·저장소·파일 테스트도 함께 실행한다. 테스트에는 개인 DB가 아닌 메모리 DB를 사용한다.

2026-09-09 검증에서는 전체 111개 테스트가 통과했다. 예약과 게시글 상태의 동시 롤백, 완료와 취소의 경쟁도 포함한다. Windows 검증 환경의 사용자 폴더 접근 제약 때문에 검증 전용 빌드 출력 폴더와 JDK 21을 사용했으며 컴파일 대상은 Java 17로 유지했다. 저장소의 Java 17 설정은 바꾸지 않았다. 브라우저에서 판매자/구매자를 나누어 신청·예약·완료와 1280px/390px 화면을 확인했다.

## 공개 저장소와 운영 서비스는 다르다

GitHub 공개는 코드 공개이지 서버 배포가 아니다. 현재 기본 설정은 학습용 H2 파일 DB와 H2 콘솔을 사용한다. 실서비스 전에 HTTPS, 전체 변경 요청의 CSRF 보호, 로그인 시도 제한, 운영 DB/백업, 비밀 설정 외부화, 파일·DB 변경의 실패 복구 정책을 별도로 점검해야 한다. 실제 개인정보가 담긴 DB/업로드 파일은 Git에 올리지 않는다.
